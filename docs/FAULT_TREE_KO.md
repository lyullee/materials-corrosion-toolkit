# Minimal cut-set fault-tree API

`reliability.fault_tree_minimal_cut_sets` accepts caller-owned basic-event probabilities and a declared set of minimal cut sets. Each cut set is an AND gate; the top event is the OR of cut sets. Exact inclusion-exclusion is used, so overlapping cut sets are handled by multiplying probabilities over the union of their basic-event IDs. Computation is bounded to 16 cut sets. The output includes Birnbaum importance (top-event probability change from setting one event probability to zero versus one) and probability-weighted importance for prioritization.

Each basic event carries a probability meaning, conditioning description and evidence digest. It may also embed the existing `IntegrityEventBasis` exchange contract; when supplied, its event ID, probability, meaning, conditioning and integrity-result digest must exactly match the basic-event fields, and the full lineage is returned. Every basic event must share one probability meaning, conditioning statement and explicit probability-scope ID. Embedded integrity-event records must also share the same clock and horizon. The caller must verify the event definitions, scope/horizon compatibility, basic-event independence, common-cause treatment and cut-set completeness. Posterior parameter probabilities and model-input uncertainty probabilities are rejected as event probabilities. The API returns `needs_data` until the four review declarations are true. Review flags are declarations, not proof.

The result is reported with the distinct `fault_tree_top_event_probability` meaning and is conditional on independent basic events and the supplied probabilities. Each supplied event retains its own probability meaning and conditioning text; callers must ensure these are compatible before review. The calculator does not derive probabilities from corrosion or structural models, harmonize incompatible horizons, infer dependence or initiating frequencies, model repair, or determine risk acceptance. Use another explicit provider for conditional dependencies or larger trees.

The synthetic request in `examples/model_inputs.json` illustrates two overlapping cut sets. Its values are fabricated and have no engineering meaning.

For inspection economics, `matintegrity.adapters.action_event_probability_from_fault_tree_result` adapts an action-specific computed FTA result to `ActionEventProbabilityEvaluation`. It requires basic-event input probabilities to mean `conditional_first_failure_in_period` and a matching `IntegrityEventBasis` with the same event probability, FTA model/version/input digest and complete result digest. A separate FTA result is required for each action whose intervention changes the event tree; the adapter does not infer action effectiveness.

`FaultTreeActionEventInput` and `inspection_action_expected_loss_inputs_from_fault_trees` combine those action results with caller-provided action definitions, costs, consequences, one baseline, review gates and evidence to produce the input contract for `inspection.action_expected_loss`. Exact action coverage and common event/horizon alignment are enforced by the existing composer. Every probability, action effect and economic assumption remains caller-owned. `evaluate_fault_tree_inspection_risk_campaign` submits the resulting inputs to the registered calculator using an explicit `RunContext` and returns a report with comparison result/input digests and each action's FTA model, input and full result digests. Open review gates are preserved as a noncomputed comparison state; no action is silently selected.
