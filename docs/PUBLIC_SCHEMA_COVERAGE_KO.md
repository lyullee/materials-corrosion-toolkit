# 등록 API 입력 스키마와 색인

`scripts/export_schemas.py`는 명시적으로 유지하는 공개·중첩 계약과 `default_registry()`의 모든 입력 계약을 합쳐 JSON Schema를 생성한다. 새 계산 API를 등록하면 입력 계약도 내보내기에 포함된다. 레지스트리에 없는 데이터 교환 계약은 기존 명시 목록으로 계속 관리한다.

생성 위치는 `docs/schemas`다. `schema_index.json`의 `models`에서 API ID에 대응하는 입력 계약 식별자·파일명·SHA-256을 찾을 수 있다. `contracts`는 독립 파일로 내보낸 계약 목록이다. 여러 API가 같은 입력 계약을 사용하면 같은 파일에 연결된다. 색인 파일 자체는 계약 스키마 수에 포함하지 않는다.

이름이 같은 서로 다른 계약은 모듈명을 포함한 파일명을 사용한다. 파일명 충돌은 덮어쓰기 전에 오류로 처리한다. 원래의 중첩 계약을 제거하거나 API 별칭 때문에 동일 계약을 중복 내보내지 않는다. 자동 포함으로 명시 목록과 레지스트리 사이의 누락을 방지한다.

권장 소비 절차는 API ID로 색인을 조회하고, 해당 파일의 SHA-256을 확인한 뒤 스키마를 읽는 것이다. 파일명만 추측하거나 디렉터리의 오래된 파일을 모두 현행 API로 해석하지 않는다. 다른 버전의 소비자는 제공자 버전과 계약 버전을 함께 고정해야 한다.

등록 입력의 스키마 연결률은 계산 실행·Python/JSON 왕복·수치 정확도·물리적 타당성·전체 개발 완료율과 다른 지표다. 스키마가 존재해도 모델에 필요한 적용 근거·자료·실행 의존성은 별도로 제공해야 한다. 실행 중 주입하는 외부 의존성은 단순 JSON 입력만으로 대신할 수 없다.

검증 코드는 `tests/test_export_schemas.py`에 있다. 등록 입력의 자동 포함, 중첩 계약 보존·중복 제거, 파일명 충돌 구분 및 색인의 실제 파일 해시를 확인한다. 생성 후에는 레지스트리의 모든 입력 계약과 색인의 실제 JSON 스키마를 다시 대조한다.

재생성 명령은 `python scripts/export_schemas.py`, 전체 대조 명령은 `python scripts/audit_schema_coverage.py`다. 프로젝트 환경의 Python을 사용한다. 감사 결과는 `artifacts/validation/registry_schema_coverage.json`에 기록한다. 모델 집합·계약 대응·파일 해시·실행 계약과 JSON의 일치 중 하나라도 어긋나면 감사는 실패한다. 해시만 새로 바꾼 잘못된 스키마도 실행 계약과의 내용 비교에서 거부한다.
